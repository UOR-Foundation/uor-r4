# [codex] Complete C1 count identity through the ordinary D11 client

## What did not work, first

Serializing the complete count model into one D11 did not fix the first wrong token. On the initial ordinary Linux client pass, both read modes still emitted ID 799 (“ We”) at offset zero on all six fixed-gold questions. Every response stopped at the 12-token cap. The independent GPU and baseline client decisions reproduced exactly. The fresh-process rerun on the final Linux executable is recorded below.

Non-author review found that the initial count-enabled loader extended the lifetime of the legacy encoded trunk and read a conflicting sidecar before rejecting it. On Wick a valid embedded header in a 1 GiB sparse envelope caused an out-of-memory failure under a 192 MiB process limit. The revised loader checked the header on the same file descriptor and rejected the conflict at 3,916 KiB RSS. It released the legacy raw trunk before loading a separate count state. Twelve old/new legacy, separate and embedded fixture arms gave byte-identical JSON. The retained Linux builds used separate Cargo target directories for the standalone tool and ordinary application after an initial dependency identity error. [Independent correction and sensitivity test](client/FIT-lifetime.md)

This meets the written-state plan's P1(a) count-identity test for this representation and slice. The independent reference is a separately reviewed record-local Rust sort on Wick. The qualifying writing device was the archived D31 RTX 5090. No GPU job or rental was required for this comparison. ## What the byte comparison permits

On the physical C1 table, a minimum raw context support of two at orders 4–10 reduced the projected count table from 2.230 GB to 544,346,506 bytes. It kept 53.24% of the raw occurrence support and 33.77% of adjusted support summed across those orders. Threshold four gave 276,123,394 bytes and kept 38.04% and 18.55%. Both candidates preserve orders 0–3 and keep each admitted context's complete successor list. These are TRAIN inventories. Their prediction effects require a new frozen artifact and fit. [Thirteen thresholds and per-order measurements](inventory/README.md)

The historical 125,998,708-byte prototype cap cannot accommodate even the C1 lower-order floor with the current complete codec and seed. That D11 costs 215,478,532 bytes before the tokenizer. At the separate four-decimal-GB P1 ceiling, the historical full-C census leaves 854,896,877 bytes for higher-order data if the cap charges the model file alone. Charging the same external tokenizer leaves **854,631,484 bytes**. The calculation preserves existing section headers, trunk and fit sizes. The full-C physical size after pruning and the quality cost remain unmeasured.
