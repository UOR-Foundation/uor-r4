# CPU training repair program

The project has used several lawful training families, and most now survive only as inactive source or dated evidence. D84 authorizes a CPU research program to repair them without changing the default GPU training path or reopening mechanisms that already failed their rules.

This page is the durable plan behind the `cpu-training-program` roadmap item. It is not evidence that any CPU trainer works.

## Boundary

- GPU remains the qualification authority. A CPU result is development research unless a later owner decision makes it a qualification path.
- Every CPU unit lives in a separately scanned Rust module, declares CPU execution, names the hardware, and has no silent GPU fallback.
- Geometry, no-squashing and no-matmul rules are unchanged.
- Each comparison uses the same tokenizer, panel, deterministic grader and count-table controls as its GPU counterpart.
- A negative closes the configuration that ran. It never erases the historical mechanism or its reopen conditions.
- Active Claude-owned float/FBS/integer files are out of scope until their current claim merges.

## Ordered work

### 1. CPU discrete writer core

Implement codebook decoding, canonical token vectors, cell admission, full-vector ranking, deterministic lower-token-ID tie-breaking, top-1/top-8, admitted-target reporting, and a reproducible row benchmark. Compare exact output with existing host oracles and stored GPU observations before adding a read.

### 2. CPU discrete training path

Add Route, Flock and Relation reads, 16-lane counterfactual proposals, strict-improvement semantics, BVG-K, staged atomic-free apply, cursor/resume and checkpoint playback one at a time. Admission is an acceptance constraint, not a post-run metric.

### 3. CPU shared-vector forward

Create a conflict-free trainer crate around:

```text
token id -> shared token vector -> route/recurrence/read -> vector point -> token
```

Prove finite forward parity against the current integer artifact before adding gradients. The input, carry and output use one token table; exact token identity stays separate from its geometric address.

### 4. CPU shared-vector training

Add rank-margin learning without softmax or dense matrix multiplication. Require deterministic update order, checkpoint identity, admission preservation and immediate exact-integer evaluation after each checkpoint.

### 5. Quantization and exact memory

Add Hamming reads and exact turn memory, then integer-aware continuation. Compare float-shadow and integer-server scores on identical rows and reject any gain that disappears after exact export.

### 6. Whole-path exact updates

Port the historical whole-path decision-recording and bounded legal-update mechanics into the isolated CPU crate after the exact writer exists. Preserve update order, acceptance checks and recovery traces, but do not import the old M2 objective or depend on `uor-r4-training`. This closes the remaining CPU reference path and supplies an exact control for the newer trainers.

### 7. CPU pilot and disposition

Run a bounded corpus pilot on the Ryzen 9 9950X only after the component parity gates pass. Report context-tokens/s, target visits/s, peak RSS, resume determinism and complete-reply/fresh-phrasing outcomes. A final disposition report marks every historical family as repaired, superseded, or retained as a rejected configuration, with links to its evidence.

## Why this order

The discrete writer is the smallest independently testable part and the arithmetic foundation of the discrete learner. The shared-vector forward then measures the current serving-aligned design before gradients add ambiguity. Training follows only after exact scoring exists. Quantization and memory come after both paths can run so their gains can be separated from a changed runtime. The corpus pilot comes last because a fast wrong trainer is not progress.

## Performance readings

Local synthetic diagnostics on the Ryzen 9 9950X recorded:

- exact outer-L1 writer rows: 216,251 rows/s on one thread and 3,034,004 rows/s on 16 threads;
- precomputed joint-pointer trunk rows: 132,385 rows/s on one thread and 1,793,613 rows/s on 16 threads;
- current synthetic integer FBS forward: about 5.4-7.5k tok/s with the native writer and 1.4-1.83k tok/s with whole-table nearest.

These are unsealed component ceilings, not training rates or language evidence. They justify building the CPU path; they do not qualify it.

## End state

The overall repair effort is complete only when every historical family has a supported, superseded or rejected disposition, the implemented paths have finite parity and deterministic resume, and at least one CPU pilot has been compared with the same evaluator and controls as its GPU counterpart. The `cpu-training-program` registration item is closed now; the child items carry the remaining work. Until that work lands, do not describe CPU training as qualified project training.
