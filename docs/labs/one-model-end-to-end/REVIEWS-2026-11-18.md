# The three external proposals, reviewed (18 Nov 2026)

Three independent reviews of an external analysis that mapped textbooks to the project's gaps. Each
verdict is against the project's *measured* blockers, not the proposal's framing.

## Verdicts

| proposal | verdict | the reason, in one line |
|---|---|---|
| **1. ID/LP + slash features** (Müller) for the "62.5 % verbatim ceiling" | **REJECT** | the premise is a panel census, not a model ceiling, and no measured blocker is addressed |
| **2. Metric data structures / cone queries** (Nievergelt) to replace turn memory | **REJECT as code, ADOPT as vocabulary and one measurement** | it describes the mechanism already served, costs more than it saves, and cannot rank a modulus partition |
| **3. Link-state / Warshall over K6** (Peterson) for context routing | **REJECT** | the transitive closure is already compiled by BFS from all 16 roots, and the K6 claim is wrong |
| **4. Cleanroom** (Sajan) | **already covered; add one practice** | FIT, power rule, adversarial review, instrument-vs-mechanism and 24 lessons exist; a gate *detection rate* does not |

## The corrections each review made to the proposal

- **"62.5 % verbatim" is panel overlap.** It is the share of *p-f's reference replies* that also appear
  in TRAIN — a data census, named that way in four records — not a generated-copy rate. The model's
  own copy rate on that line was **0.4–1.2 %**, and the current panel's DEV is **75 %** verbatim.
- **"K6 / 15 semiprime edges" is wrong three ways.** `ORBIT = 16` is the node set; the 15 is the
  **Cl(0,6) bivector count**, not K6's edges; an icosahedron has 12 vertices and 30 edges.
- **The route is already solved at compile time.** `compile_geometry` runs BFS from every one of the 16
  roots and stores the operator, edge history and inverse for all 256 pairs, with a test for every
  pair. Warshall would duplicate it and Dijkstra has no weights to minimise.
- **A grammar would cost 4–6 units before one gate**, and the project already built and parked a
  24,944-line dependent-language mechanism with the record "0 of 8 proposed replacements helped".
  A PCFG is a normalized exponential, banned by §3.2 by name.
- **A metric index cannot pay.** Per token: the port address is **~0.5 k** operations, the centroid
  address **~393 k**, the candidate inventory ~262 k, the whole-table nearest 8.4 M. Trees do not beat
  a 256-entry scan when distances concentrate in 512-D, and a plane sweep's pruning bound is useless
  when one axis carries 1/512 of the distance. The writer is **32 ms of a 792 ms step (4 %)**; the
  address is 0.5 k of that, so any index wins **< 0.01 %** — refused by the plan's 20 % rule.

## The finding that matters

**Admission is at chance.** Eight kept cells of 32 slots cover `8 × 32 / 8,192 = 3.125 %` of the
table; measured admission is **2.9 %** — *slightly below chance*. **The cell tells the writer nothing
about which token is right**, because the cells are `token-id mod 256`: a modulus partition with no
metric structure. No tree, grid or cone can find which arbitrary id class holds the target — *to know
which cell to open you must already know which token is right.*

So the readout defect is not the address and not the index: **it is the partition.** That also
explains why the port address and the centroid address can both look reasonable and still admit 2.9 %,
and it is the same limit that caps the vocabulary at 8,192 (256 cells × 32).

**The fix, in order:**

1. **Measure it**: `P(target's cell ∈ kept 8)` under `ports` and under `centroids` on the 101,175-row
   DEV — the queued address A/B already prints `admitted`. Gate: centroids **≥ 8 %** (2.6× chance).
2. If both stay near 3.1 %, the partition is confirmed and the next unit is a **geometric
   re-partition**: cells defined by the table's own geometry (orbit roots, cluster structure) rather
   than by `id mod 256`. That lifts admission *and* the vocabulary ceiling in one change.
3. Then the ordered codex-52 A/B on the **pick** (gate ≥ 3.0 %, 3.7× today), never the hinge.

## What was adopted from the external analysis

- **The centre + radius ("location vs extension") vocabulary**, free: the ports are centres, and the
  cells' **extension is unused** — which is the seed of a geometric re-partition.
- **The gate-detection-rate practice**: one ledger row per gate, the gate, the deliberate break, and
  caught or missed. It is the one Cleanroom element the project lacks, and its absence is why two GPU
  runs were spent on a control that could not discriminate.

## What was not adopted, and why

A parser, a link-state router, an octree, a plane sweep, a Cleanroom waterfall, and a formal spec of
the cone query. Each either describes what is already served, targets a stage that is 4 % of the step,
or adds state that the one-native-state rule would have to carry bit-identically for no measured gain.

## The `MetricCone` prototype, tested (18 Nov)

The prototype was compiled verbatim rather than reviewed, in `/tmp/opencode/mcone2`.

**It does not compile.** The test module calls `VectorState::from_raw()` with no argument in four
places, against `fn from_raw(coords: [Q31; BLOCK_DIM])` — four `E0061`s.

**With only that repaired, its central test fails.** Every entry is built at the origin, so all three
distances are 0 and the documented tie-break (most recent `turn_index` on an exact tie) returns
**103, not the asserted 102**. The comments claim "Candidate 1: Chebyshev = 50, Candidate 2: 30,
Candidate 3: 80 (outside radius 60)"; no entry carries those coordinates. The expected values are
asserted, not measured. The other two tests pass and are trivial (zero distance to itself; the
`i32::MAX`/`i32::MIN` span is `u32::MAX`).

**It is a linear scan, not an index.** `query_nearest_in_cone` and `query_k_candidates_in_cone` are
`for entry in entries`. There is no grid, tree, partitioning or prune anywhere in the code, so the
documented `O(log N)` "Grid File / Quadtree" claim is not implemented — it is `O(N)` over the memory
array, which is worse than the turn memory's one open-addressed probe.

**It scores different lanes and a different metric.** `BLOCK_DIM = 8`; the writer scores the mean L1
over **512** lanes. `max |q-c|` over 8 lanes is not the writer's quantity, so adopting it is a model
change, not an optimisation. For pruning it is also mostly useless on the real metric: the writer
minimises the **mean** L1 over 512 lanes, and an 8-lane sum only bounds it as `sum8/512` — 1/64 of
the 8-lane mean. (The bound is sound for `L_inf`, where `max_512 >= max_8`; that is the one true
statement in the proposal, and it costs a metric change to use.)

**Two integration claims are wrong.** `ReadSpec` is at `crates/uor-r4-discrete/src/lib.rs:169`, not
`src/read.rs`, and it is documented as "artifact identity, not an inference-time override", with a
strict serde `Wire` enum (`deny_unknown_fields`) and a `validate()` that bounds `kept` 1..=8 — none
of which the spec's §4 mentions, and all of which a new variant must satisfy. `discrete.turn_memory`
is not a symbol in the tree; the turn memory is `TurnMemory` projected to `FbsMemorySnapshot`
(`crates/uor-r4-float-train/src/fbs_export.rs:802`).

## The finding: the substance already exists, with controls, and was never measured on admission

`crates/uor-r4-discrete/src/address_cells.rs` already implements the geometric re-partition, as a
treatment/control family:

| construction | control |
|---|---|
| `StructuredV1` (`address_structured_v1`) | `ShuffledV1 { seed }` |
| `FullVectorV1` | `FullVectorShuffledV1 { seed }` |
| `WiderBlocksV1` | `WiderBlocksShuffledV1 { seed }` |
| `EMeansV1 { seed }` (fitted predecessor clusters) | — |

and `AddressMetric` already carries the location/extension idea as two oracles: `OuterL1V1` (the
two-block key every model uses), **`CellEnvelopeL1V1`** (`cell_envelope_l1`) and
`FullVectorCellL1V1` (`full_vector_cell_l1`). That is "centre + envelope" as a *metric*, which is
the only form in which it can rank anything.

It has a measured address win: `address_structured_v1` gives a TRAIN predecessor L1 total of
**22,374,488**, which is **-33.94 %** against `P8` (33,871,344) and **-25.12 %** against its shuffled
control `S8` (29,881,384) — `docs/integration/current-state.md:1155`.

**But its admission effect was never measured.** `docs/labs/address-cells-codebook-2026-10-19/README.md`
says: "Host data preparation only. **No admission was estimated on the host (D24).**"

So the honest next unit is not to port a scan. It is to **measure the admission of the partition that
already exists**: `P(target's cell in the kept 8)` under the structured placement against its shuffled
control, on the same table and the same rows. The project's own rule is treatment-versus-control, and
the control is already built. Gate: structured clearly above both chance (3.125 %) and its own
shuffled control; anything else falsifies the re-partition the same way the route precompute was
falsified at 3 %.
