# Plan revision, 19 Nov 2026 — the path, after the readout was measured

Supersedes the order in `PLAN-2026-11-18.md` where the two disagree. The 18 Nov plan's *judgement* was
right — "C5 is decisive", "no capability claim from a metric a count table also passes", "no scale
before C5". What today changed is that **C5 as written cannot be measured**, and that is the thing to
fix before spending another six-hour run.

## What is settled

- **The readout was the defect, and it is fixed.** Same trunk, only the address changed:
  `ports` admitted 2.3 % and picked 0.4 %; `centroids` admitted **12.0 %** and picked **8.1 %**
  (`nearest` identical within each pair). C2 is answered; the partition work is not authorised.
- **The run is now training with `centroids`**, so the served model carries the readout instead of
  losing nine answers in ten. It produces C1 and the mature checkpoint; it changes nothing else.

## The three real defects, in order of what they cost

### 1. There is no instrument that can say whether this model is competitive

C5 asks for "top-1 at 4.5 M / 30 M / 100 M against published dense scaling curves". **Published curves
are in loss or perplexity. This line has no likelihood**: the readout ranks by distance, and a
normalised exponential is banned by §3.2. So the decisive rung of the plan has no common axis with the
thing it wants to compare against, and every capability claim the project makes is therefore
unfalsifiable. That is a bigger problem than any layer's cost.

**The fix is an instrument, not a run.** The model already produces a ranking, and the target's rank
is computable — `nearest_rank` and `FloatTokenRank`/`IntegerTokenRank` already exist
(`bin/packet-parity.rs:342`, used today only for float-vs-integer parity). Add one reading:

    bits/token  =  mean over rows of log2(rank(target) + 1)

Applied **identically** to the model and to a count table, this gives both a number on the same axis.
Against published work it is an **optimistic bound**: a rank code ignores how much probability the
model puts on rank 1 versus rank 2, so it flatters the model. That asymmetry is what makes it
decisive in one direction:

> **If the model's optimistic bound at 30 M values is worse than a published 30 M dense model's true
> bits per token, C5 is answered negative — no amount of scale closes it.**

That test needs the checkpoints we already have and no new GPU time. It is the cheapest way to learn
whether this project has a path at all, and it should have been the first measurement, not the fifth.

### 2. The only bar is a bigram

`BLOCKERS` already says it: "beats T2" means "is a better count table". C1 passing would therefore
prove only that the model is *not worse than a bigram* — which is exactly the kind of claim the plan's
own refusal list forbids. **Fix:** an interpolated bigram/trigram count model on the same dev, same
tokens, same vocabulary. C1 is then a **floor**, and the first honest capability milestone becomes
"clearly above a trigram, with the gap widening over training."

### 3. Throughput bounds the token budget, and the token budget bounds capability

The layer costs ~63 ms per 1,024 rows — **~200× a dense layer** — so five hours buys 343 M tokens. At
30 M parameters that is a toy by any published account, and no architectural change fixes it. **Fix,
before any scale run:** U4 (fuse the q16 conversion and the gate into the gather — one pass instead of
three over the same ~2 M values per projection) and the batch sweep M2 unblocked. A 3–4× throughput
win is worth more than any tweak at this size, because it multiplies tokens seen.

## The order now

| # | step | cost | gate |
|---|---|---|---|
| 1 | **bits/token instrument** on the existing checkpoints, and the same for T2 | 1 unit, no new GPU | the number exists and is reproducible on a re-run |
| 2 | **interpolated T2/T3 bar** on the same dev | 1 unit, host | C1 restated as a floor against the stronger bar |
| 3 | **U4 + batch sweep**: the layer's per-element passes fused | 1–2 units, GPU | ≥20 % fewer µs/token, else reverted |
| 4 | **C5 with the instrument**: optimistic bound vs published curves | 1 unit of analysis | decisive either way |
| 5 | **C6 scale** — only if 4 is not negative | days | U2 measured, corpus built once |

The running job stays queued as it is: it produces C1's floor and the checkpoint, and it is the last
run of that kind until step 4 says scaling is worth anything.

## What this refuses

- Another long run whose reading changes no decision.
- A capability claim against a bigram.
- A scale run before the instrument exists.
- Calling C5 "decisive" while it has no axis.
