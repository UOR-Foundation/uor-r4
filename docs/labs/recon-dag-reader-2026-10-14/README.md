# The DAG reader: an on-demand backend, and two claims that are not the same claim

**Date:** 2026-10-14 · **Lab:** DeepSeek · **Line:** no model line — tooling/instrument · **Count:** 0/3
**Owning work:** PM tasking — the reconstruction-DAG production reader (crate `uor-r4-recon-dag`)

## What it replaces

The byte-DAG experiment at `docs/labs/spiralcore-native-attention-review-2026-10-14/evidence/cs/range_reader.rs`
loads **every** record into a `HashMap<Id, Node>` before answering any range query, and its own evidence README
says so: *"the experiment is not an end-to-end low-memory reader"*, with manifest, envelope, index and
construction costs explicitly excluded. Its final line is the second half of the gap:
**`whole_object_sha256_in_rust=NOT_CHECKED`**.

## The two halves

**1. An on-demand backend.** The records file is a fixed-stride sequence of `1-byte scale || 12-byte id ||
32-or-36-byte data`, so `IndexedBackend` builds a `HashMap<Id, offset>` by walking **headers alone** — 13
bytes per node and no node data — and reads a record's bytes only when a traversal visits it. `EagerBackend`
keeps the experiment's behaviour and is retained as the reference.

**2. Two digest claims, kept apart.** A node id authenticates **the nodes a range touched**. It says nothing
about the nodes outside the range, and nothing about the object. `RangeVerified { nodes, unverified_nodes }`
therefore reports its **unverified remainder** rather than letting the weaker claim pass as the stronger one,
and `WholeObject { digest }` is the only variant that carries object integrity.

**The owner's rule is what shapes the API:** *on the main track a read must always be verified*. So the strong
claim is a **separate entry point** (`read_whole_object(manifest, backend, expected_digest)`) rather than a flag
on the range read: a caller cannot reach integrity by forgetting to ask for it, and `Read::whole_object_verified`
is the single question a main-track consumer asks.

## Verified

| test | what it establishes |
|---|---|
| `both_backends_agree_byte_for_byte` | 203 ranges, eager vs indexed: **identical bytes**, both equal to the source |
| `the_indexed_backend_does_not_read_records_outside_the_range` | corrupting the **last** record leaves a 64-byte range read clean, while the whole-object read fails on it — **the record was never read**, and the corruption is real |
| `a_consistent_dag_can_still_reconstruct_the_wrong_object` | **the reason the crate exists**: two DAGs that differ in one bit are both internally consistent; node ids cannot tell them apart, and only the declared whole-object digest refuses the wrong one — while it verifies against its own |
| `a_range_read_reports_what_it_did_not_cover` | `nodes + unverified_nodes == the whole store`, and `whole_object_verified()` is **false** for a range read |
| `a_whole_object_read_is_the_strong_claim` | the strong claim verifies, and a wrong digest is **refused** rather than reported |
| `a_corrupt_record_is_caught` | a tampered node is `Error::Integrity` |

Fixtures are **built in Rust by the test file** (leaf = 32 bytes, parent = three child ids, ladder derived from
the atom count) because the experiment's fixtures are generated by a JS script from pinned sources and are not
committed.

## Stated rather than hidden

* **Nothing consumes this crate yet.** It is the reader, delivered with its tests; wiring it into a
  reconstruction path is a separate step.
* **It is shaped to consume Codex's D19 object store rather than compete with it.** The `Backend` trait is the
  seam: the store supplies bytes, this crate supplies traversal and the verification claims. I have flagged the
  coupling on #2028 so the `RangeVerified`/`WholeObject` distinction can be settled once, in the store's read
  contract, with this as its first client.
* **The whole-object digest is SHA-256** (the workspace's existing dependency), while node ids are the crate's
  own 12-byte digest over `scale || data`. They are different functions making different claims, and the
  `NOT_CHECKED` line in the experiment's output is exactly the gap between them.
* **`IndexedBackend` reopens the file per node.** Correct and simple; a mmap or a held handle is the obvious
  next optimisation and is not claimed here.
